## 1. Introduction
예전에는 직접 가서 필요한 걸 구매했지만 현재는 직접 가서 구매하는 것보다 온라인 구매가 시간적, 가격적으로 편리하여 식사, 생필품 모든 것을 배달로 해결하는 추세이다. 이러한 변화는 공동구매라는 소비 문화를 발생시킨다. 여기서 공동구매는 구매를 원하는 사람들끼리 모여 동일한 상품을 다량으로 구매하여 물류 비용을 절감하는 장점을 가진다. 더불어 1인 가구가 늘어남에 따라 공동구매는 물건에만 국한되지 않고 음식을 배달할 때 발생하는 최소금액을 충족하기 위해 이루어지기도 한다. 특히 이러한 공동구매는 SNS에서 자주 볼 수 있는데 아래의 사진 2개를 보면 다량의 물건을 구매할 때 저렴한 금액으로 구매가 가능하다보니 친구 혹은 인근에 거주하는 사람들끼리 나눠서 구매하기를 원하는 게시글과 댓글을 보고 이러한 과정을 더 간편하게 실현할 수 있도록 프로그램을 구축하고자 한다.

DealMate는 앞서 말했듯 위치 기반으로 이루어져 사용자가 거주 지역을 인증하여 공동 구매에 참여하고 같은 지역의 다른 사용자와 특별 할인 정보를 공유할 수 있도록 지원한다. 단순히 공동구매방을 만들고 참여하는 기능 외에도 결제 및 정산 관련 문제를 투명하게 처리하도록 설계하는 걸 목표로 한다. 이는 공동구매 방을 개설한 호스트가 대표로 구매를 성공하면 시스템은 참여자 수를 기준으로 총 결제 금액과 1인당 정산 금액을 계산하고 이 과정에서 호스트는 실제 결제한 영수증을 업로드한다. 이후 참여자들은 호스트의 영수증 인증과 개인 송금 정보 인증 과정을 확인할 수 있다. 이러한 절차는 사용자 신뢰를 높이고 공동구매 과정에서 발생할 수 있는 결제 금액 오류나 정산 누락을 줄이기 위해 마련된다. 더 나아가 공동구매가 완료되면 리뷰 기능을 제공한다. 리뷰 기능의 목적은 정산 이행 여부 등을 바탕으로 사용자들이 평가하여 다른 사용자들은 향후 공동구매를 하거나 호스트를 선택할 때 이러한 리뷰를 참고하여 신뢰도를 높이는 이유이다. 이를 위해선 관리자는 누적된 리뷰와 사용자 데이터를 분석하여 문제를 발생시킨 사용자를  활동 24시간 활동 제한이나 계정 영구정지 등의 조치를 취할 수 있다.

결과적으로 이 디자인 문서는 분석 단계에서 도출된 요구사항을 실제로 구현 가능한 구조로 구현하는 것을 목표로 한다. DealMate 시스템의 전반적인 구조를 다이어그램으로 시각화하여 이를 통해 시스템의 기능 흐름과 객체 간의 협력 관계를 더 쉽게 이해 가능하고 구현 단계에서 각 클래스의 역할과 관계를 기반으로 코드를 더욱 체계적으로 작성한다. 사용자는 기본적으로 User로 정의하고, 공동구매 방을 생성하는 Host, 공동구매에 참여하는 Member, 사용자를 관리하는 Administrator로 구분하였다.

5) Create Group Purchase Room
 <img width="626" height="524" alt="image" src="https://github.com/user-attachments/assets/ce3825b9-730c-4432-b145-359b7decf3de" />

호스트는 GroupPurchaseRoom 객체를 요청하여 상품명과 인원수와 같은 변수를 입력한다. Database에 방 정보를 저장한다. Database에서 저장 완료 응답이 오면  GroupPurchaseRoom 는 Host에게 방 생성 완료를 알린다.

6) Join Group Purchase
<img width="579" height="471" alt="image" src="https://github.com/user-attachments/assets/41010cee-6e2e-47ef-a480-38d7db6b25c2" />

Member은 공동구매 참여 요청을 한다. GroupParticipation은 Member가 요청한 방의 참여 가능 여부를 확인하고 자리가 없을 경우 반환, 자리가 있을 경우 참여 정보를 Database에 저장한다. 저장이 성공하면 GroupParticipation에 완료 응답을 보내고 Member에게 참여 성공을 반환한다.

7) Requset Settlement
 <img width="737" height="548" alt="image" src="https://github.com/user-attachments/assets/1e79423c-371d-49a8-a8d4-dce8f0a1556c" />

메인 화면에서 Host가 공동구매 탭에서 결제 영수증을 업로드하면 Host 클래스의 uploadPaymentReceipt(receiptImage) 메소드가 실행된다. Host 클래스는 PaymentReceipt 클래스에게 uploadReceipt(receiptImage)를 요청하여 이미지를 저장한다. PaymentReceipt 클래스의 extractAmountByOCR(receiptImage) 메소드는 이미지에서 결제된 금액을 추출한다. OCR로 금액 추출 성공 시 PaymentReceipt 객체의 ocrAmount 값이 finalAmount에 반영되어 Database 클래스의 saveData(receipt) 메소드를 통해 영수증 정보가 저장된다. Host 클래스의 requestSettlement(roomId) 메소드를 실행하여 해당 공동구매 방의 정산 요청을 진행한다. 만약 금액 추출에 실패한 경우에는 finalAmount에 Host가 수동 입력값을 반영한 뒤 다시 정산 요청이 진행된다.

8) Calculate Settlement Amount
<img width="690" height="518" alt="image" src="https://github.com/user-attachments/assets/093b4fa2-0f22-4535-aca2-190c5379cc1f" />

   
main에서 Host에게 정산 요청을 보내면 Host 클래스의 requestSettlement(roomId) 메소드가 실행된다.
Host 클래스는 Settlement 클래스의 calculateAmount(totalAmount, count) 메소드를 호출하여 총 결제 금액과 참여 인원수를 전달한다.
Settlement 클래스에서는 전달받은 totalAmount와 count를 이용하여 1인당 정산 금액을 계산한다.
계산이 완료되면 updateSettlementStatus(status) 메소드를 통해 정산 상태를 갱신한다.
참여 인원수가 0보다 큰 경우 Database 클래스의 saveData(settlement) 메소드를 호출하여 계산된 정산 정보를 저장한다.
Database는 저장이 완료되면 saveData() 응답을 반환한다.
Settlement는 calculateAmount() 응답을 Host에게 반환하고, Host는 requestSettlement() 응답을 main에게 반환한다.
참여 인원수가 0 이하인 경우에는 정산 금액을 계산할 수 없으므로 오류 처리한다.

9) Transfer Proof Verification
 <img width="697" height="503" alt="image" src="https://github.com/user-attachments/assets/aa359342-005f-405b-885f-526ade5abc41" />

 Host가 Settlement에 송금 인중을 전달하면 Settlement가 TransferProof에 송금 인증 이미지를 업로드한다. TransferProof가 인중 상태를 "confirmed"로 업데이트하고 TransferProof가 인종 결과를 Settlement에 반환한다. Settlement가 정산 상태를 완료상태 completed로 업데이트한다. 상태 업데이트 결과를 Host에 반환하면 main(화면)에 업로드 완료를 알린다.

10) Write Review
 <img width="724" height="503" alt="image" src="https://github.com/user-attachments/assets/fb7fcb3b-0ab3-4672-99d1-98c9eabd2cfb" />

main에서 사용자가 리뷰 작성 기능을 실행하면 User 클래스의 writeReview(rating, content) 메소드가 호출된다.
User 클래스는 Review 클래스에게 writeReview(rating, content)를 요청하여 별점과 리뷰 내용을 전달한다.
Review 클래스에서는 전달받은 rating과 content를 이용하여 리뷰 정보를 생성한다.
리뷰 작성 후 Review 클래스의 updateAverageRating() 메소드가 실행되어 대상 사용자의 평균 별점이 갱신된다.
갱신된 리뷰 정보는 Database 클래스의 saveData(review) 메소드를 통해 저장된다.
Database는 저장 처리가 완료되면 saveData() 응답을 Review 클래스에게 반환한다.
Review 클래스는 writeReview() 응답을 User 클래스에게 반환하고, User 클래스는 최종적으로 main에게 writeReview() 응답을 반환한다.

11) Manage User

    <img width="724" height="506" alt="image" src="https://github.com/user-attachments/assets/b0a94075-62b2-42d5-b8d2-87e3a8af6c55" />

main에서 관리자가 사용자 관리 화면을 실행하면 Administrator 클래스의 showLowRatingUsers() 메소드가 호출된다.
Administrator 클래스는 AdministratorManagement 클래스의 showLowRatingUsers() 메소드를 통해 평균 별점이 낮은 사용자 목록을 요청한다.
AdministratorManagement 클래스는 관리 대상 사용자 목록을 ArrayList<User> 형태로 반환한다.
관리자가 특정 사용자를 선택하고 관리 조치를 적용하면 AdministratorManagement 클래스의 applyManagementAction(actionType) 메소드가 실행된다.
actionType 값이 "restrict"인 경우 Administrator 클래스의 restrictUser(userId) 메소드를 호출하여 해당 사용자를 활동 제한 처리한다.
활동 제한 처리 후 Database 클래스의 saveData(management) 메소드를 통해 관리 조치 정보를 저장한다.
actionType 값이 "suspend"인 경우 Administrator 클래스의 suspendUser(userId) 메소드를 호출하여 해당 사용자를 계정 정지 처리한다.
계정 정지 처리 후 Database 클래스의 saveData(management) 메소드를 통해 관리 조치 정보를 저장한다.
Database 클래스는 저장이 완료되면 saveData() 응답을 AdministratorManagement 클래스에게 반환한다.
AdministratorManagement 클래스는 최종적으로 applyManagementAction() 응답을 main에게 반환하여 사용자 관리 조치가 완료되었음을 알린다.

## 4.1 Client State Machine Diagram

### 상태 목록 및 설명

| 상태                         | 설명                                                                                                                                                                                                                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Idle                       | 앱이 실행된 후 사용자의 선택을 기다리는 초기 상태이다. 사용자는 이 상태에서 회원가입 또는 로그인을 선택할 수 있다. 사용자가 회원가입을 선택하면 Registration 상태로 전이되고, 로그인을 선택하면 Login Verification 상태로 전이된다.                                                                                                                                               |
| Registration               | 사용자가 회원가입 정보를 입력하는 상태이다. 사용자는 userId, password, email 등의 정보를 입력한다. 회원가입 요청이 성공하면 Neighborhood Certification 상태로 전이되고, 입력 오류 또는 중복 아이디가 발생하면 Idle 상태로 돌아간다.                                                                                                                                     |
| Neighborhood Certification | 회원가입 이후 사용자의 동네 인증을 수행하는 상태이다. 사용자의 위치 또는 선택 지역을 기준으로 동네 인증을 진행한다. 동네 인증이 성공하면 Login Verification 상태로 전이되고, 인증 실패 시 Idle 상태로 돌아간다.                                                                                                                                                             |
| Login Verification         | 사용자가 아이디와 비밀번호를 입력하여 로그인을 시도하는 상태이다. 입력된 로그인 정보를 확인하고, 일반 사용자와 관리자를 구분한다. 일반 사용자 로그인에 성공하면 User Session 상태로 전이되고, 관리자 로그인에 성공하면 Admin Session 상태로 전이된다. 로그인에 실패하면 Idle 상태로 돌아간다.                                                                                                               |
| User Session               | 일반 사용자로 로그인된 상태를 나타내는 복합 상태이다. User Session 안에는 Home, Post Writing, Group Purchase List, Group Room Creation, Group Participation, Settlement Management, Review Writing 상태가 포함된다. 일반 사용자는 이 상태에서 특가 정보 글 작성, 공동구매 방 생성, 공동구매 참여, 정산 확인, 리뷰 작성 기능을 사용할 수 있다. logout 이벤트가 발생하면 Logout 상태로 전이된다. |
| Home                       | 일반 사용자가 로그인한 뒤 처음 진입하는 기본 화면 상태이다. 사용자는 홈 화면에서 특가 정보 글을 확인하거나, 글쓰기 또는 공동구매 기능으로 이동할 수 있다. 특가 정보 글 작성을 선택하면 Post Writing 상태로 전이되고, 공동구매 메뉴를 선택하면 Group Purchase List 상태로 전이된다.                                                                                                                  |
| Post Writing               | 사용자가 특가 정보 게시글을 작성하는 상태이다. 사용자는 제목과 내용을 입력하여 게시글을 작성한다. 게시글 저장이 완료되면 다시 Home 상태로 돌아간다.                                                                                                                                                                                                         |
| Group Purchase List        | 사용자가 공동구매 방 목록을 확인하는 상태이다. 사용자는 모집 중인 공동구매 방을 확인할 수 있고, 방을 직접 생성하거나 기존 방에 참여할 수 있다. Host로 방을 생성하는 경우 Group Room Creation 상태로 전이되고, Member로 방에 참여하는 경우 Group Participation 상태로 전이된다.                                                                                                            |
| Group Room Creation        | Host가 공동구매 방을 생성하는 상태이다. 상품명, 최대 참여 인원, 예상 금액 등의 정보를 입력하여 공동구매 방을 생성한다. 방 생성이 완료되면 Group Purchase List 상태로 돌아간다.                                                                                                                                                                               |
| Group Participation        | Member가 공동구매 방에 참여하는 상태이다. 참여 가능 인원을 확인한 뒤 공동구매 방에 참여한다. 공동구매 참여가 완료되고 구매가 진행되면 Settlement Management 상태로 전이된다.                                                                                                                                                                                |
| Settlement Management      | 공동구매 완료 후 정산을 확인하고 처리하는 상태이다. Host는 영수증을 업로드하고 정산을 요청할 수 있으며, Member는 정산 금액을 확인하고 송금 인증 이미지를 업로드할 수 있다. 정산이 완료되면 Review Writing 상태로 전이된다.                                                                                                                                                      |
| Review Writing             | 공동구매가 완료된 후 사용자가 리뷰를 작성하는 상태이다. 사용자는 거래 상대방에 대한 별점과 리뷰 내용을 작성한다. 리뷰 저장이 완료되면 Home 상태로 돌아간다.                                                                                                                                                                                                    |
| Admin Session              | 관리자로 로그인된 상태를 나타내는 복합 상태이다. Admin Session 안에는 Admin Home과 User Management 상태가 포함된다. 관리자는 낮은 별점 사용자를 확인하고, 사용자 관리 조치를 수행할 수 있다. logout 이벤트가 발생하면 Logout 상태로 전이된다.                                                                                                                               |
| Admin Home                 | 관리자가 로그인한 뒤 처음 진입하는 관리자 기본 화면 상태이다. 관리자는 이 상태에서 저평점 사용자 목록을 확인하고 사용자 관리 기능으로 이동할 수 있다. 사용자 관리를 선택하면 User Management 상태로 전이된다.                                                                                                                                                                  |
| User Management            | 관리자가 저평점 사용자를 조회하고 관리 조치를 수행하는 상태이다. 관리자는 사용자를 선택하여 활동 제한 또는 계정 정지 조치를 적용할 수 있다. 관리 조치가 완료되면 Admin Home 상태로 돌아간다.                                                                                                                                                                              |
| Logout                     | 일반 사용자 또는 관리자가 로그아웃을 수행한 상태이다. 로그아웃이 완료되면 클라이언트의 활동이 종료되고 Final State로 전이된다.                                                                                                                                                                                                                   |

## 4.2 Server State Machine Diagram

Server State Machine Diagram은 DealMate 서버가 클라이언트 요청을 수신하고 처리하는 과정을 표현한 것이다. 서버는 요청을 대기하다가 클라이언트 요청을 받으면 요청을 검증하고, 요청 유형에 따라 기능을 처리한다. 이후 데이터베이스를 갱신하고 클라이언트에게 응답을 반환한다.



| 상태                        | 설명                                                                                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Waiting Request           | 서버가 클라이언트 요청을 기다리는 초기 상태이다. 클라이언트에서 회원가입, 로그인, 게시글 작성, 공동구매, 정산, 리뷰, 관리자 조치 등의 요청이 들어오면 Request Validation 상태로 전이된다.                                                                                                                                               |
| Request Validation        | 서버가 수신한 요청의 유효성을 검증하는 상태이다. 요청에 필요한 값이 존재하는지, 형식이 올바른지, 로그인 세션이나 권한이 적절한지 확인한다. 요청이 유효하면 Request Processing 상태로 전이되고, 요청이 유효하지 않으면 Error Response 상태로 전이된다.                                                                                                        |
| Request Processing        | 서버가 요청 종류에 따라 실제 기능을 처리하는 복합 상태이다. Request Processing 안에는 Request Type Check, Account Processing, Post Processing, Group Purchase Processing, Settlement Processing, Admin Processing 상태가 포함된다. 서버는 요청 유형을 확인한 뒤 알맞은 처리 상태로 이동한다.                                  |
| Request Type Check        | 수신된 요청이 어떤 기능에 해당하는지 확인하는 상태이다. 요청이 회원가입, 로그인, 동네 인증과 관련되어 있으면 Account Processing 상태로 전이된다. 게시글 작성 요청이면 Post Processing 상태로, 공동구매 방 생성 또는 참여 요청이면 Group Purchase Processing 상태로 전이된다. 정산 관련 요청이면 Settlement Processing 상태로, 관리자 조치 요청이면 Admin Processing 상태로 전이된다. |
| Account Processing        | 회원가입, 로그인, 동네 인증과 관련된 요청을 처리하는 상태이다. 회원가입 요청이 들어오면 register(user)를 수행하고, 로그인 요청이 들어오면 login(id, pw)를 수행한다. 동네 인증 요청이 들어오면 requestCertification(location)을 처리한다. 처리가 완료되면 Request Processing 내부의 종료 상태로 전이된다.                                                       |
| Post Processing           | 특가 정보 게시글 작성 요청을 처리하는 상태이다. 사용자가 입력한 제목과 내용을 바탕으로 writePost(title, content)를 수행하고, savePost()를 통해 게시글 저장을 처리한다. 처리가 완료되면 Request Processing 내부의 종료 상태로 전이된다.                                                                                                       |
| Group Purchase Processing | 공동구매 방 생성 또는 참여 요청을 처리하는 상태이다. Host가 공동구매 방을 생성하는 경우 createRoom()을 수행하고, Member가 공동구매 방에 참여하는 경우 joinRoom()을 수행한다. 참여 인원 변경이 필요한 경우 updateParticipantCount()를 수행한다. 처리가 완료되면 Request Processing 내부의 종료 상태로 전이된다.                                                   |
| Settlement Processing     | 정산과 관련된 요청을 처리하는 상태이다. Host가 영수증을 업로드하면 uploadReceipt(receiptImage)를 수행하고, OCR로 금액을 추출한 뒤 calculateAmount(totalAmount, count)를 통해 1인당 정산 금액을 계산한다. Member가 송금 인증 이미지를 업로드하면 uploadTransferProof(transferImage)를 처리한다. 처리가 완료되면 Request Processing 내부의 종료 상태로 전이된다. |
| Admin Processing          | 관리자의 사용자 관리 요청을 처리하는 상태이다. 관리자는 showLowRatingUsers()를 통해 낮은 별점 사용자를 조회하고, applyManagementAction(actionType)을 통해 활동 제한 또는 계정 정지 조치를 수행한다. 처리가 완료되면 Request Processing 내부의 종료 상태로 전이된다.                                                                              |
| Database Update           | 요청 처리가 완료된 후 데이터베이스를 갱신하는 상태이다. 회원 정보, 게시글 정보, 공동구매 방 정보, 참여 정보, 정산 정보, 리뷰 정보, 관리자 조치 정보 등이 저장되거나 수정된다. 데이터 갱신이 완료되면 Response Sending 상태로 전이된다.                                                                                                                    |
| Response Sending          | 서버가 클라이언트에게 처리 결과를 반환하는 상태이다. 요청 처리 성공 또는 실패 결과를 클라이언트로 전달한다. 응답 전송이 완료되면 서버는 다시 Waiting Request 상태로 돌아가 다음 요청을 기다린다.                                                                                                                                              |
| Error Response            | 요청 검증 실패 또는 처리 오류가 발생했을 때 오류 응답을 생성하는 상태이다. 필수 입력값 누락, 잘못된 로그인 정보, 권한 부족, 잘못된 요청 형식 등이 발생하면 Error Response 상태로 전이된다. 오류 응답을 생성한 뒤 Response Sending 상태로 전이된다.                                                                                                       |
