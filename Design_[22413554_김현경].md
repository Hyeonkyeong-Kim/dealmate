## 1. Introduction
예전에는 직접 가서 필요한 걸 구매했지만 현재는 직접 가서 구매하는 것보다 온라인 구매가 시간적, 가격적으로 편리하여 식사, 생필품 모든 것을 배달로 해결하는 추세이다. 이러한 변화는 공동구매라는 소비 문화를 발생시킨다. 여기서 공동구매는 구매를 원하는 사람들끼리 모여 동일한 상품을 다량으로 구매하여 물류 비용을 절감하는 장점을 가진다. 더불어 1인 가구가 늘어남에 따라 공동구매는 물건에만 국한되지 않고 음식을 배달할 때 발생하는 최소금액을 충족하기 위해 이루어지기도 한다. 특히 이러한 공동구매는 SNS에서 자주 볼 수 있는데 아래의 사진 2개를 보면 다량의 물건을 구매할 때 저렴한 금액으로 구매가 가능하다보니 친구 혹은 인근에 거주하는 사람들끼리 나눠서 구매하기를 원하는 게시글과 댓글을 보고 이러한 과정을 더 간편하게 실현할 수 있도록 프로그램을 구축하고자 한다.

DealMate는 앞서 말했듯 위치 기반으로 이루어져 사용자가 거주 지역을 인증하여 공동 구매에 참여하고 같은 지역의 다른 사용자와 특별 할인 정보를 공유할 수 있도록 지원한다. 단순히 공동구매방을 만들고 참여하는 기능 외에도 결제 및 정산 관련 문제를 투명하게 처리하도록 설계하는 걸 목표로 한다. 이는 공동구매 방을 개설한 호스트가 대표로 구매를 성공하면 시스템은 참여자 수를 기준으로 총 결제 금액과 1인당 정산 금액을 계산하고 이 과정에서 호스트는 실제 결제한 영수증을 업로드한다. 이후 참여자들은 호스트의 영수증 인증과 개인 송금 정보 인증 과정을 확인할 수 있다. 이러한 절차는 사용자 신뢰를 높이고 공동구매 과정에서 발생할 수 있는 결제 금액 오류나 정산 누락을 줄이기 위해 마련된다. 더 나아가 공동구매가 완료되면 리뷰 기능을 제공한다. 리뷰 기능의 목적은 정산 이행 여부 등을 바탕으로 사용자들이 평가하여 다른 사용자들은 향후 공동구매를 하거나 호스트를 선택할 때 이러한 리뷰를 참고하여 신뢰도를 높이는 이유이다. 이를 위해선 관리자는 누적된 리뷰와 사용자 데이터를 분석하여 문제를 발생시킨 사용자를  활동 24시간 활동 제한이나 계정 영구정지 등의 조치를 취할 수 있다.

결과적으로 이 디자인 문서는 분석 단계에서 도출된 요구사항을 실제로 구현 가능한 구조로 구현하는 것을 목표로 한다. DealMate 시스템의 전반적인 구조를 다이어그램으로 시각화하여 이를 통해 시스템의 기능 흐름과 객체 간의 협력 관계를 더 쉽게 이해 가능하고 구현 단계에서 각 클래스의 역할과 관계를 기반으로 코드를 더욱 체계적으로 작성한다. 사용자는 기본적으로 User로 정의하고, 공동구매 방을 생성하는 Host, 공동구매에 참여하는 Member, 사용자를 관리하는 Administrator로 구분하였다.

5) Create Group Purchase Room
 <img width="626" height="524" alt="image" src="https://github.com/user-attachments/assets/ce3825b9-730c-4432-b145-359b7decf3de" />

호스트는 GroupPurchaseRoom 객체를 요청하여 상품명과 인원수와 같은 변수를 입력한다. Database에 방 정보를 저장한다. Database에서 저장 완료 응답이 오면  GroupPurchaseRoom 는 Host에게 방 생성 완료를 알린다.

6) Join Group Purchase
<img width="579" height="471" alt="image" src="https://github.com/user-attachments/assets/41010cee-6e2e-47ef-a480-38d7db6b25c2" />

Member은 공동구매 참여 요청을 한다. GroupParticipation은 Member가 요청한 방의 참여 가능 여부를 확인하고 자리가 없을 경우 반환, 자리가 있을 경우 참여 정보를 Database에 저장한다. 저장이 성공하면 GroupParticipation에 완료 응답을 보내고 Member에게 참여 성공을 반환한다.

7) Requset Settlement
 <img width="737" height="548" alt="image" src="https://github.com/user-attachments/assets/1e79423c-371d-49a8-a8d4-dce8f0a1556c" />

메인 화면에서 Host가 공동구매 탭에서 결제 영수증을 업로드하면 Host 클래스의 uploadPaymentReceipt(receiptImage) 메소드가 실행된다. Host 클래스는 PaymentReceipt 클래스에게 uploadReceipt(receiptImage)를 요청하여 이미지를 저장한다. PaymentReceipt 클래스의 extractAmountByOCR(receiptImage) 메소드는 이미지에서 결제된 금액을 추출한다. OCR로 금액 추출 성공 시 PaymentReceipt 객체의 ocrAmount 값이 finalAmount에 반영되어 Database 클래스의 saveData(receipt) 메소드를 통해 영수증 정보가 저장된다. Host 클래스의 requestSettlement(roomId) 메소드를 실행하여 해당 공동구매 방의 정산 요청을 진행한다. 만약 금액 추출에 실패한 경우에는 finalAmount에 Host가 수동 입력값을 반영한 뒤 다시 정산 요청이 진행된다.

8) Calculate Settlement Amount
<img width="690" height="518" alt="image" src="https://github.com/user-attachments/assets/093b4fa2-0f22-4535-aca2-190c5379cc1f" />

   
main에서 Host에게 정산 요청을 보내면 Host 클래스의 requestSettlement(roomId) 메소드가 실행된다.
Host 클래스는 Settlement 클래스의 calculateAmount(totalAmount, count) 메소드를 호출하여 총 결제 금액과 참여 인원수를 전달한다.
Settlement 클래스에서는 전달받은 totalAmount와 count를 이용하여 1인당 정산 금액을 계산한다.
계산이 완료되면 updateSettlementStatus(status) 메소드를 통해 정산 상태를 갱신한다.
참여 인원수가 0보다 큰 경우 Database 클래스의 saveData(settlement) 메소드를 호출하여 계산된 정산 정보를 저장한다.
Database는 저장이 완료되면 saveData() 응답을 반환한다.
Settlement는 calculateAmount() 응답을 Host에게 반환하고, Host는 requestSettlement() 응답을 main에게 반환한다.
참여 인원수가 0 이하인 경우에는 정산 금액을 계산할 수 없으므로 오류 처리한다.

9) Transfer Proof Verification
 <img width="697" height="503" alt="image" src="https://github.com/user-attachments/assets/aa359342-005f-405b-885f-526ade5abc41" />

 Host가 Settlement에 송금 인중을 전달하면 Settlement가 TransferProof에 송금 인증 이미지를 업로드한다. TransferProof가 인중 상태를 "confirmed"로 업데이트하고 TransferProof가 인종 결과를 Settlement에 반환한다. Settlement가 정산 상태를 완료상태 completed로 업데이트한다. 상태 업데이트 결과를 Host에 반환하면 main(화면)에 업로드 완료를 알린다.

10) Write Review
 <img width="724" height="503" alt="image" src="https://github.com/user-attachments/assets/fb7fcb3b-0ab3-4672-99d1-98c9eabd2cfb" />

main에서 사용자가 리뷰 작성 기능을 실행하면 User 클래스의 writeReview(rating, content) 메소드가 호출된다.
User 클래스는 Review 클래스에게 writeReview(rating, content)를 요청하여 별점과 리뷰 내용을 전달한다.
Review 클래스에서는 전달받은 rating과 content를 이용하여 리뷰 정보를 생성한다.
리뷰 작성 후 Review 클래스의 updateAverageRating() 메소드가 실행되어 대상 사용자의 평균 별점이 갱신된다.
갱신된 리뷰 정보는 Database 클래스의 saveData(review) 메소드를 통해 저장된다.
Database는 저장 처리가 완료되면 saveData() 응답을 Review 클래스에게 반환한다.
Review 클래스는 writeReview() 응답을 User 클래스에게 반환하고, User 클래스는 최종적으로 main에게 writeReview() 응답을 반환한다.

11) Manage User
main에서 관리자가 사용자 관리 화면을 실행하면 Administrator 클래스의 showLowRatingUsers() 메소드가 호출된다.
Administrator 클래스는 AdministratorManagement 클래스의 showLowRatingUsers() 메소드를 통해 평균 별점이 낮은 사용자 목록을 요청한다.
AdministratorManagement 클래스는 관리 대상 사용자 목록을 ArrayList<User> 형태로 반환한다.
관리자가 특정 사용자를 선택하고 관리 조치를 적용하면 AdministratorManagement 클래스의 applyManagementAction(actionType) 메소드가 실행된다.
actionType 값이 "restrict"인 경우 Administrator 클래스의 restrictUser(userId) 메소드를 호출하여 해당 사용자를 활동 제한 처리한다.
활동 제한 처리 후 Database 클래스의 saveData(management) 메소드를 통해 관리 조치 정보를 저장한다.
actionType 값이 "suspend"인 경우 Administrator 클래스의 suspendUser(userId) 메소드를 호출하여 해당 사용자를 계정 정지 처리한다.
계정 정지 처리 후 Database 클래스의 saveData(management) 메소드를 통해 관리 조치 정보를 저장한다.
Database 클래스는 저장이 완료되면 saveData() 응답을 AdministratorManagement 클래스에게 반환한다.
AdministratorManagement 클래스는 최종적으로 applyManagementAction() 응답을 main에게 반환하여 사용자 관리 조치가 완료되었음을 알린다.
